# MCP Agent — Portfolio MCP Server

A Model Context Protocol (MCP) server that exposes the tools of the Meeting Intelligence Agent to any MCP-compatible client — including Claude Desktop. Instead of going through a UI, Claude can autonomously query meeting data, search transcripts, and retrieve action items directly from a natural language conversation.

**Portfolio:** [notion.so/Lander-Iglesias-ed9bca668ca08368ab0c81aed0869e1d](https://www.notion.so/Lander-Iglesias-ed9bca668ca08368ab0c81aed0869e1d)

---

## The problem

The Meeting Intelligence Agent has a web UI — which is fine for demos but not for real workflows. If you want to ask "what does Carlos have pending this week?", you open a browser, navigate to the demo, and interact with the interface. That friction kills adoption.

The better experience: open Claude Desktop, ask the question in natural language, and get the answer from the actual database — no UI, no navigation, no copy-pasting.

---

## Solution

An MCP server written in Python that exposes 6 tools connected to the real PostgreSQL database of the Meeting Intelligence Agent. Claude Desktop connects to the server at startup and can autonomously decide which tool to call — and when — based on what you ask.

**The key difference from a REST API:**
With a REST API, *you* decide when to call which endpoint and with which parameters. With MCP, *Claude* reasons about which tool it needs and calls it autonomously. You never say "use the list_meetings tool" — you say "what meetings do I have?" and Claude figures it out.

## Architecture

```
Claude Desktop
      │
      │ MCP Protocol (stdio)
      ▼
MCP Server (Python)
      │
      ├── list_meetings()
      ├── get_meeting_summary()
      ├── get_meeting_extractions()
      ├── search_meeting()
      ├── ask_meeting()
      └── list_action_items_by_owner()
      │
      ▼
PostgreSQL 16 + pgvector (port 5433)
Meeting Intelligence Agent database
```

## Tools

**`list_meetings`**
Lists all meetings analyzed and stored in PostgreSQL, ordered by date. Claude uses this first to identify which meeting the user is asking about.

**`get_meeting_summary`**
Returns the executive summary and key topics for a specific meeting. Generated by Claude Haiku during the Meeting Intelligence pipeline and stored in PostgreSQL.

**`get_meeting_extractions`**
Returns the full structured output for a meeting: decisions, action items (with owner, deadline, and priority), open questions, and pending topics.

**`search_meeting`**
Semantic search over a meeting's transcript chunks using cosine similarity via pgvector. Returns the top-k most relevant chunks for a given query.

**`ask_meeting`**
Full RAG pipeline: searches the most relevant chunks with pgvector, then calls Claude Haiku to generate a grounded answer. Claude answers only from the actual transcript content — not from memory.

**`list_action_items_by_owner`**
Filters action items for a specific person across a meeting. "What does Carlos have pending?" routes here.

## Key technical decisions

**Why stdio instead of HTTP?**
For local Claude Desktop integration, stdio is the simplest and most reliable transport — no port management, no authentication, no network configuration. The server runs as a subprocess launched and managed by Claude Desktop. For a production deployment where the server needs to be accessible remotely, SSE over HTTP would be the right choice.

**Why connect to the existing Meeting Intelligence database instead of creating a new one?**
The data is already there. The Meeting Intelligence Agent indexes transcripts into PostgreSQL with pgvector during analysis. The MCP server reads from the same database without duplicating data or infrastructure. The separation of concerns is clean: the Meeting Intelligence Agent writes, the MCP server reads.

**Why `sys.path.insert` instead of relative imports?**
Claude Desktop launches the server as a standalone process, not as part of the Python package. Relative imports (`from ..nodes...`) only work when the module is loaded as part of a package. `sys.path.insert` adds the project root to Python's module search path so absolute imports work regardless of how the process is launched.

**Tool granularity — why 6 tools instead of 1?**
Claude reasons better with focused, single-purpose tools than with one generic tool that does everything. `list_meetings` + `get_meeting_extractions` is two small, predictable operations. A single `query_meetings` tool that does both would be harder for Claude to reason about and harder to debug when something goes wrong.

---

## Limitations

- **Local only (stdio transport).** The server runs as a subprocess on the same machine as Claude Desktop. Remote access would require converting to SSE transport.
- **Read-only.** The MCP server only reads from PostgreSQL — it cannot create, update, or delete meetings. Writes happen through the Meeting Intelligence Agent pipeline.
- **Requires the Meeting Intelligence database to be running.** If the PostgreSQL container is stopped, all tools fail with a connection error.
- **No authentication.** The server trusts any MCP client that connects. For production, tool-level access control would be needed.

## Setup

**1. Start the Meeting Intelligence PostgreSQL container:**
```bash
docker run -d --name meeting_intel_db \
  -e POSTGRES_USER=your_user \
  -e POSTGRES_PASSWORD=your_password \
  -e POSTGRES_DB=meeting_intel \
  -p 5433:5432 \
  pgvector/pgvector:pg16
```

**2. Add to Claude Desktop config** (`%APPDATA%\Claude\claude_desktop_config.json` on Windows):
```json
{
  "mcpServers": {
    "portfolio-mcp": {
      "command": "path/to/.venv/Scripts/python.exe",
      "args": ["path/to/backend/agents/mcp_agent/server.py"],
      "cwd": "path/to/AI-Portfolio"
    }
  }
}
```

**3. Restart Claude Desktop.** The server appears as a connected tool in the connectors panel.

## Example conversations

```
You: What meetings do I have analyzed?
Claude: [calls list_meetings] You have 3 meetings: Q3 Product Planning (Jun 2),
        Q2 Planning (May 28), and a duplicate of Q3.

You: What were the action items from Q2?
Claude: [calls get_meeting_extractions] Carlos has two high-priority items:
        post the job offer by Friday and send the DB migration estimate by Monday.

You: What was decided about authentication in Q3?
Claude: [calls ask_meeting with RAG] The team decided to ship with custom JWT
        to avoid delaying the September 15th launch. OAuth migration was
        scheduled for Q4 as acknowledged technical debt.
```
